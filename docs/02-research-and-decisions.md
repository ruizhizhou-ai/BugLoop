# BugLoop 调研与方案决策

> 本文件的核心职责：沉淀开源产品调研、自研依据和最终方案决策，不作为具体实现规则来源。章节编号沿用 `BugLoop_SPEC_v1.0` 原编号，便于追溯。

## 五、前期技术调研

在确定采用自研方案之前，需要先调研现有 Bug / Issue 管理系统，判断：

> **现成开源产品能不能直接满足需求，如果不能，是进行二次开发更合适，还是重新开发一个轻量工具更合适。**

技术调研主要从以下几个维度进行：

1. 是否支持 Bug 提交；
2. 是否支持人员指派；
3. 是否支持状态流转；
4. 是否支持附件和截图；
5. 是否支持评论和操作记录；
6. 是否支持修复和验收闭环；
7. 是否支持 Markdown 或文档管理；
8. 是否支持文档历史版本；
9. 系统是否轻量；
10. 是否适合公司内部快速部署；
11. 二次开发成本；
12. 是否符合现有 Java 技术体系；
13. 后续扩展 GitLab、企业微信等能力是否方便。

经过初步调研，重点评估了：

- 禅道 ZenTao；
- Redmine；
- MantisBT；
- Plane；

几种方案。

## 六、开源方案调研

### 6.1 禅道 ZenTao

禅道是国内比较成熟的研发项目管理平台，本身具备非常完整的 Bug 生命周期。

官方 Bug 流程包括：

```Plain
提交Bug
→ 确认Bug
→ 解决Bug
→ 验证Bug
→ 关闭Bug
```

如果验证失败，还可以重新激活 Bug，再次进入处理流程。

这和本项目所需要的：

```Plain
提交
→ 指派
→ 修复
→ 验收
→ 关闭
```

实际上非常接近。

同时禅道开源版还提供项目、产品、任务、Bug、测试、文档、DevOps、看板等大量功能，也支持私有化部署和 API。

#### 优点

- Bug 管理流程成熟；
- 支持指派；
- 支持问题描述和截图；
- 支持修复和验证；
- 支持重新激活 Bug；
- 中文化程度高；
- 支持私有化部署；
- 有比较成熟的项目管理能力；
- 后续能力比较全面。

#### 存在的问题

本项目当前只是一个内部轻量 Bug 工具，而禅道定位是完整研发项目管理平台。

即使官方支持单独使用 Bug 管理模块，在使用 Bug 功能时仍然具有产品、项目、测试等禅道自身的业务模型。

对于当前项目而言：

```Plain
需求管理
产品管理
项目管理
测试用例
测试计划
版本管理
Sprint
DevOps
BI
```

大部分暂时不需要。

因此存在：

> **功能较重，系统模型大于实际需求。**

如果为了让禅道变成一个极简内部工具，再进行较多页面、流程和字段定制，就会引入额外的学习和二次开发成本。

## 七、Redmine 调研

Redmine 是一个比较成熟的开源 Issue / 项目管理平台。

它支持：

- Issue；
- 人员指派；
- 优先级；
- 附件；
- 评论；
- 自定义字段；
- 权限；
- 自定义状态；
- 工作流；
- REST API。

Redmine 可以根据角色和 Issue 类型配置允许发生的状态转换，因此可以实现：

```Plain
待处理
   ↓
处理中
   ↓
待验收
   ↓
已关闭
```

这种状态流转。

它的 REST API 同样支持 Issue 创建、修改、负责人以及附件等操作。

#### 优点

- 相对成熟稳定；
- Issue 功能完善；
- 工作流灵活；
- 权限体系成熟；
- API 完整；
- 支持附件；
- 支持私有化部署；
- 功能相比完整研发平台更聚焦。

#### 存在的问题

Redmine 本身仍然是一个通用项目管理平台，不是专门按照公司当前 Bug 处理模式设计。

例如本项目比较强调：

```Plain
Markdown详细问题文档
文档编辑
文档历史版本
独立修复说明
固定验收流程
内部极简操作界面
```

如果完全按照现有需求进行适配，仍然需要进行插件开发或者二次开发。

另外，Redmine 本身采用 Ruby on Rails 技术体系。

而当前开发人员主要使用：

```Plain
Java
Spring Boot
Vue
```

如果后续需要深入修改 Redmine，本身还需要额外维护一套不同技术体系，长期维护成本并不一定低。

因此 Redmine 更适合：

> 直接使用它现有流程。

而不是：

> 大量修改成为完全符合公司内部习惯的小工具。

## 八、MantisBT 调研

MantisBT 是一个比较纯粹的开源 Bug Tracking 系统，相比禅道和 Redmine更加聚焦 Bug 本身。

它支持 Bug 创建、处理、人员、状态以及历史记录。

其中一个比较有价值的功能是 Bug History。

MantisBT 会记录 Bug 从创建到关闭过程中的修改，例如：

- 修改时间；
- 操作人员；
- 修改字段；
- 修改前的值；
- 修改后的值。

这和当前系统希望实现的“操作可追溯”非常接近。

#### 优点

- 功能比较专注；
- 相对轻量；
- Bug Tracking 能力成熟；
- 操作历史比较完整；
- 部署成本较低。

#### 存在的问题

MantisBT 更偏传统 Bug Tracker，在：

```Plain
现代化界面
Markdown详细文档体验
文档版本管理
公司自定义验收流程
后续业务扩展
```

方面与项目需求存在一定差异。

MantisBT 使用 PHP 开发。

如果后续要进行大量定制，同样需要额外维护并不熟悉的技术体系。

因此：

> 如果需求只是标准 Bug Tracking，MantisBT 是比较合适的。

但如果需要形成一个符合公司内部习惯的小型产品，仍然存在一定二开成本。

---

## 九、Plane 调研

Plane 是相对较新的开源项目管理 / Issue Tracking 产品，界面和交互方式更加现代。

其 Community Edition 支持：

- 自托管；
- Projects；
- Work Items；
- Pages；
- Dashboard；
- REST API；
- Webhook。

并且 Community Edition 采用 AGPL-3.0，可以自行部署。

#### 优点

- UI 比较现代；
- Issue 管理体验较好；
- 支持文档；
- 自托管；
- API/Webhook 能力较完整；
- 产品体验比传统 Bug Tracker 更好。

#### 存在的问题

Plane 本身的定位仍然是项目协作平台，并不只是 Bug 系统。

另外，官方目前将一些更高级的：

```Plain
Workflow
Approval
Audit Trail
```

能力放在商业版本。

而本项目恰好比较强调：

> 状态流转、验收和全过程操作记录。

因此，如果完全基于 Community Edition 使用，还需要进一步验证相关功能能否完全覆盖当前内部流程。

从当前一期需求来看，引入 Plane 的整体系统复杂度仍然高于实际需要。

## 十、开源方案对比

基于当前项目需求，可以得到以下初步对比。

| 方案 | Bug 闭环 | 轻量程度 | Markdown / 文档 | 自定义流程 | 技术栈匹配 | 二开成本 | 当前适合程度 |
|---|---|---|---|---|---|---|---|
| 禅道 ZenTao | 很强 | 一般 | 强 | 强 | 一般 | 中 | 较高 |
| Redmine | 强 | 较好 | 一般 | 强 | 较低（Ruby） | 中高 | 较高 |
| MantisBT | 强 | 强 | 一般 | 较强 | 较低（PHP） | 中高 | 一般 |
| Plane | 较强 | 一般 | 强 | 高级流程部分受版本限制 | 一般 | 中 | 一般 |

需要说明的是：

> 这个评价不是说明自研产品比成熟开源产品更好，而是基于当前项目规模和公司实际需求进行匹配度判断。

## 十一、为什么最终没有直接使用开源系统

经过技术调研以后，没有直接使用现有开源系统，主要有以下几个原因。

### 11.1 当前需求非常聚焦

目前真正需要的功能只有：

```Plain
Bug提交
截图附件
Markdown详细文档
人员指派
优先级
处理状态
修复说明
验收
评论
操作日志
```

并不需要：

```Plain
需求管理
Sprint
项目管理
工时管理
测试用例
发布管理
甘特图
复杂DevOps
```

如果直接采用完整项目管理系统，会引入大量当前阶段用不到的功能。

---

### 11.2 希望降低使用门槛

这个系统不仅可能给开发人员使用，也可能让：

- 产品；
- 业务；
- 测试；
- 运维；
- 普通内部员工；

提交问题。

因此希望用户进入系统以后非常简单：

```Plain
发现问题
→ 提交Bug
→ 上传截图
→ 等待处理
→ 验收
```

而不是需要理解：

```Plain
产品
项目
迭代
需求
任务
版本
测试单
```

等研发管理概念。

---

### 11.3 Markdown 文档是本项目重点能力

本项目并不只是填写一个简单 Bug Description。

希望一个 Bug 本身就是一份相对完整的问题文档：

```Plain
问题现象
重现步骤
期望结果
实际结果
环境
截图
补充说明
```

并且后续还希望支持：

```Plain
编辑
预览
图片
代码块
历史版本
```

因此 Markdown 文档在这个系统里属于核心能力，而不是附属字段。

自研可以围绕这一体验进行专门设计。

---

### 11.4 公司内部流程可以直接固化

现有开源系统通常提供非常通用的工作流。

而本项目实际流程比较简单：

```Plain
待处理
→ 处理中
→ 待验收
→ 已关闭
```

验收失败：

```Plain
待验收
→ 重新打开
→ 处理中
```

自研以后可以直接在后端通过状态机控制，不需要为了适配通用系统进行大量配置。

---

### 11.5 技术栈更加统一

项目采用：

```Plain
Vue3
+
Spring Boot
+
MySQL
```

与目前开发人员熟悉的技术体系一致。

后续出现问题或者增加功能，不需要额外维护其他语言和框架。

---

### 11.6 后续扩展更可控

虽然第一期只建设 Bug 闭环，但未来可能扩展：

```Plain
企业微信通知

GitLab集成

Bug关联Commit

Bug关联Merge Request

代码修改统计

Dashboard

Bug处理效率分析
```

如果采用自研系统：

```Plain
数据库模型
API
页面
业务流程
```

都能够直接控制。

后续扩展不会受到第三方产品内部数据模型的过多限制。

---

### 11.7 Vibe Coding降低了自研成本

传统方式开发一个完整内部管理工具，CRUD、列表、表单、权限以及基础页面会占用较多开发时间。

目前可以通过 Vibe Coding 辅助完成：

```Plain
项目脚手架
CRUD
Vue页面
接口
SQL
表单
Markdown编辑器接入
日志模块
```

从而明显降低一个轻量内部系统从零开发的成本。

因此在当前项目规模下：

> **自研成本已经降低到可以接受的范围。**

这也是最终选择自研的重要条件之一。

---

## 十二、最终技术决策

综合考虑：

```Plain
需求匹配度
+
系统复杂度
+
用户使用成本
+
二次开发成本
+
技术栈匹配
+
后续维护
+
未来扩展能力
```

最终决定：

> **不直接采用完整开源 Bug 管理系统，而是参考禅道、Redmine、MantisBT 等成熟产品的 Bug 工作流和设计思路，自研一个符合公司实际使用场景的轻量 Bug 闭环管理工具。**

这里不是完全“重复造轮子”。

主要借鉴成熟产品的：

```Plain
Bug生命周期
状态流转
人员指派
操作历史
验收机制
```

然后只实现公司真正需要的功能。
