# BugLoop 产品需求

> 本文件的核心职责：说明项目为什么做、面向谁、一期做什么，以及核心业务流程和页面范围。章节编号沿用 `BugLoop_SPEC_v1.0` 原编号，便于追溯。

## 一、项目名称

**内部 Bug 闭环管理系统**

项目定位：面向公司内部使用的轻量级 Bug 收集、处理、验收和追踪工具。

---

## 二、项目背景

目前公司内部部分业务系统、后台系统或者代码出现 Bug 后，主要通过微信群、私聊等方式进行反馈和沟通。

这种方式沟通比较方便，但是随着问题数量增加，逐渐暴露出以下问题：

1. Bug 信息比较分散，问题描述、截图、处理结果散落在聊天记录中；
2. Bug 缺少统一状态，无法快速判断当前是待处理、处理中还是已经解决；
3. 责任人不明确，容易出现问题提出以后无人持续跟进；
4. Bug 处理进度不可见，需要反复通过微信询问；
5. 修复完成以后缺少正式的验收过程；
6. 历史 Bug 难以查询和追溯；
7. 问题描述被修改以后，缺少历史版本记录；
8. 无法形成统一的问题处理数据，为后续统计分析提供基础。

因此计划开发一个轻量级内部 Bug 闭环管理工具，将目前依赖微信群的非结构化问题反馈方式，转变为：

> **统一提交、明确负责人、状态可跟踪、修复有记录、结果有验收、全过程可追溯。**

---

## 三、项目目标

第一阶段不建设复杂的研发管理平台，而是聚焦 Bug 管理本身，实现：

```Plain
Bug提交
   ↓
人员指派
   ↓
问题处理
   ↓
填写修复说明
   ↓
提交验收
   ↓
验收通过 / 驳回
   ↓
Bug关闭 / 重新处理
```

主要目标包括：

- 通过工作空间对不同团队、部门或业务范围进行隔离；
- 支持工作空间创建、切换和成员管理；
- 建立统一 Bug 入口；
- 支持 Markdown 详细问题描述；
- 支持截图及附件；
- 明确 Bug 处理负责人；
- 明确 Bug 当前处理状态；
- 记录修复原因和解决方案；
- 建立修复后的验收机制；
- 支持评论和问题沟通；
- 自动记录关键操作；
- Markdown 修改可以进行历史追溯；
- 为后续代码关联、通知和统计分析预留扩展能力。

## 四、前期需求确认

正式开发之前，首先需要和实际使用人员确认业务范围和流程，而不是直接进入编码阶段。

### 4.1 使用人员

初步划分以下几类人员。

#### Bug 提交人

负责：

- 创建 Bug；
- 填写问题描述；
- 上传截图；
- 补充问题信息；
- 查看处理进度；
- 发表评论；
- 对修复结果进行验收。

#### Bug 处理人员

主要是开发或者相关技术人员，负责：

- 查看指派给自己的 Bug；
- 开始处理；
- 更新状态；
- 填写修复说明；
- 提交验收；
- 回复评论。

#### 管理人员

负责：

- 用户管理；
- Bug 指派；
- Bug 转派；
- 特殊情况下修改状态；
- 查看全部 Bug。

第一阶段不建设复杂的 RBAC 权限平台，而采用满足当前需求的简单角色权限。

### 4.2 工作空间需求

为了支持不同团队、部门或业务系统分别使用本系统，同时避免所有 Bug 混在同一个数据池中，第一期增加**工作空间（Workspace）**作为系统最上层的数据组织和隔离单位。

一个用户可以加入多个工作空间，每个 Bug 必须归属于一个工作空间。用户进入系统后，可以在自己有权限的工作空间之间进行切换。

示例：

```Plain
研发中心
├── BUG-1001 登录异常
├── BUG-1002 支付异常
└── BUG-1003 订单查询异常

内部管理系统
├── BUG-2001 OA审批异常
└── BUG-2002 考勤页面异常
```

第一期工作空间主要支持：

- 创建工作空间；
- 编辑工作空间名称和说明；
- 切换工作空间；
- 查看当前工作空间成员；
- 添加成员；
- 移除成员；
- 修改成员角色；
- 停用工作空间；
- 重新启用已停用的工作空间；
- 工作空间之间的 Bug 数据隔离。

第一期不建议直接物理删除已经产生业务数据的工作空间，优先采用“启用 / 停用”方式进行管理。

工作空间角色保持简单，暂不建设复杂 RBAC：

#### Owner

工作空间创建者或负责人，可以：

- 编辑工作空间；
- 管理成员；
- 设置管理员；
- 查看当前工作空间全部 Bug；
- 指派和转派 Bug。

#### Admin

工作空间管理员，可以：

- 管理成员；
- 查看当前工作空间全部 Bug；
- 指派和转派 Bug；
- 协助处理异常状态。

#### Member

普通成员，可以：

- 提交 Bug；
- 查看当前工作空间允许查看的 Bug；
- 处理指派给自己的 Bug；
- 评论；
- 对自己负责验收的 Bug 进行验收。

同时明确以下规则：

> **Bug 的负责人和验收人默认只能从当前工作空间成员中选择。**

工作空间本身只承担人员组织和数据隔离职责，不引入 Sprint、需求、任务、工时等复杂项目管理概念。

## 十三、核心业务流程设计

第一期采用简单明确的 Bug 生命周期：

```Plain
创建Bug
   ↓
待处理
   ↓
负责人开始处理
   ↓
处理中
   ↓
填写修复说明
   ↓
提交验收
   ↓
待验收
   ↓
       ┌───────────────┐
       │               │
    验收通过         验收失败
       ↓               ↓
     已关闭          重新打开
                       ↓
                     处理中
```

人员指派属于 Bug 信息变化，不单独设置“已指派”状态。

---

## 十四、第一期功能范围

第一期严格控制在：

1. 工作空间管理；
2. 工作空间成员管理；
3. 工作空间切换与数据隔离；
4. Bug 提交；
5. Markdown 详细说明；
6. Markdown 编辑；
7. Markdown 历史版本；
8. 截图附件；
9. 人员指派；
10. 优先级；
11. Bug 状态；
12. 修复说明；
13. 验收；
14. 评论；
15. 操作日志；
16. Bug 查询筛选。

暂不开发：

```Plain
复杂Dashboard
GitLab
代码统计
企业微信机器人
需求管理
项目管理
任务管理
测试用例
Sprint
工时
```

## 十五、Markdown 文档设计

Bug 问题描述采用 Markdown。

默认模板例如：

```Markdown
# 问题现象

描述发现的问题。

## 重现步骤

1. 第一步
2. 第二步
3. 第三步

## 实际结果

描述当前结果。

## 期望结果

描述正常情况下的结果。

## 环境

- 系统：
- 版本：
- 浏览器：

## 补充说明

其他信息。
```

支持：

```Plain
标题
列表
表格
代码块
引用
链接
图片
编辑
预览
粘贴截图
```

数据库保存：

```Plain
description_md
```

而不是直接保存最终 HTML。

---

## 十六、Markdown 历史版本

当前版本保存到：

```Plain
bug.description_md
```

历史版本单独保存：

```Plain
bug_description_history
```

记录：

```Plain
Bug ID
版本
内容
修改人
修改时间
```

例如：

```Plain
V1 李四 09:30
V2 李四 10:15
V3 张三 11:20
```

这样即使 Bug 描述被修改，也能够进行历史追溯。

---

## 十七、附件设计

附件支持：

- PNG；
- JPG；
- PDF；
- TXT；
- 日志文件等。

文件不直接保存进 MySQL。

第一阶段：

```Plain
服务器文件目录
```

后续可以切换：

```Plain
MinIO
```

MySQL 保存附件元数据。

---

## 十八、优先级设计

第一阶段采用四级：

```Plain
P0 紧急

P1 高

P2 中

P3 低
```

暂时不同时设计“Severity + Priority”两套概念，避免增加使用复杂度。

---

## 十九、修复及验收设计

开发人员处理完成以后，需要填写修复说明：

```Markdown
## 问题原因

## 修复方案

## 影响范围

## 验证方式
```

然后执行：

```Plain
提交验收
```

状态：

```Plain
处理中 → 待验收
```

验收人可以：

```Plain
验收通过
→ 已关闭
```

或者：

```Plain
验收失败
→ 重新打开
```

验收失败必须填写原因。

---

## 二十、评论与操作日志

评论用于人员主动沟通。

例如：

```Plain
李四：
生产环境昨天也出现过一次。

张三：
已经定位，是空指针问题。
```

操作日志由系统自动生成。

例如：

```Plain
09:30 李四创建Bug

09:35
负责人：
无 → 张三

10:03
张三
状态：
待处理 → 处理中

11:25
张三
状态：
处理中 → 待验收

14:30
李四验收通过

14:30
状态：
待验收 → 已关闭
```

操作日志原则上不可由普通用户修改或者删除。

工作空间级别的关键操作也需要留痕，例如：

```Plain
创建工作空间
修改工作空间
添加成员
移除成员
修改成员角色
停用工作空间
重新启用工作空间
```

建议单独使用：

```Plain
workspace_operation_log
```

记录工作空间级别的操作，避免与 Bug 操作日志混在一起。

## 二十一、页面设计

一期主要页面：

```Plain
工作空间切换

首页

Bug管理
├── 全部Bug
├── 我提交的
├── 指派给我的
└── 待我验收

提交Bug

Bug详情

成员管理

工作空间设置
```

用户登录后默认进入最近使用的工作空间，也可以通过顶部工作空间切换器切换到其他已加入的工作空间。

其中 Bug 详情页是整个系统的核心页面。

包括：

```Plain
基础信息

Markdown问题描述

附件

修复说明

状态操作

验收

评论

操作日志

历史版本
```
